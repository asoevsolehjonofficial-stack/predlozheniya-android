## 3. Архитектура и критические ограничения

### 3.1 Текущий путь сборки

1. Пользователь описывает приложение или вставляет HTML.
2. Сайт получает HTML и показывает его в iframe.
3. API проверяет запрос и помещает HTML в очередь.
4. GitHub Actions забирает исходник и проверяет его как HTML.
5. Workflow копирует файл в Android assets и собирает оболочку WebView.
6. APK проверяется на целостность/подпись, после чего возвращается через защищённый API.

Этот путь подходит для веб-приложений внутри WebView, но не даёт автоматически доступ к Android MediaStore, фоновым сервисам, системным уведомлениям, MediaSession, Bluetooth, контактам и другим нативным возможностям.

### 3.2 Важные находки для следующего этапа

- **Нет многофайлового нативного входа.** Контракт сборки принимает поле `html`, а workflow ожидает файл `index.html`. Нет проверенного входа для Kotlin/Java, ресурсов, AndroidManifest и зависимостей как единого Android-проекта.
- **Опасно просто разрешить произвольный Gradle ZIP.** Gradle-файлы проекта исполняют код. Перед запуском нативной сборки необходимы изоляция, ограничения ресурсов/времени/сети, безопасная обработка архива, запрет выхода из рабочей директории, контроль зависимостей и отдельные права CI.
- **Проверка APK не равна проверке функций.** Проверка ZIP/подписи/checksum подтверждает целостность артефакта; запуск activity в эмуляторе не доказывает, что кнопки, хранение данных, музыка или фоновые операции работают правильно.
- **Есть альтернативная реализация Worker.** `backend/wrangler.toml` запускает `backend/src/index.js`, тогда как `backend/worker.js` содержит отдельную реализацию похожего API. До изменения архитектуры надо установить, какие части дублируются и какая версия является авторитетной; нельзя случайно исправить неиспользуемый файл вместо развёрнутого.
- **Документация о хранении расходится.** `backend/README.md` описывает временное хранение HTML и APK в KV, а `docs/SECURE_ANDROID_BUILDS.md` упоминает private R2 для пользовательских APK. Реальный код активного Worker следует считать источником истины до отдельной проверки развёрнутых bindings.
- **Проверка готовности сервиса ограничена.** Успешный health endpoint подтверждает только те условия конфигурации, которые он проверяет. Его нельзя считать сквозным тестом реальной сборки или установки.
- **Сетевые возможности намеренно ограничены.** Генерируемому HTML добавляется ограничительная CSP, блокирующая сетевые подключения по умолчанию. Это защитное решение, но оно также означает, что приложения с сетевыми функциями требуют отдельно спроектированного и проверенного разрешённого пути.
- **Подпись не означает релиз в Google Play.** Наличие ключа и корректной подписи не заменяет release-конфигурацию, проверку обновления существующей установки, privacy review и функциональное тестирование.

## 6. Решение и критерии перехода к этапу 2

Полный этап 1 пока **НЕ завершён**: отсутствует успешная сквозная сборка пользовательского APK с реальной очередью, эмуляторным запуском и проверкой защищённой загрузки. Перед изменением архитектуры требуется согласовать внутренний контракт нативного проекта. Безопасный старт — не произвольное исполнение загруженного Gradle ZIP, а контролируемый генератор проекта с поддерживаемым набором шаблонов/возможностей и allowlist зависимостей. Расширять список нативных возможностей следует постепенно, тестируя каждую реальную функцию.

**Переход к этапу 2:** сохранить текущий HTML/WebView-путь как отдельный тип «веб-приложение», спроектировать отдельный тип «нативный Android-проект» и разделить их схемы входных данных, проверки, сборку и критерии готовности. Макет смартфона не менять до прохождения этапов 1–6.

## 9. Найденная причина недоступности сквозного smoke-теста и исправление в PR

При проверке пунктов 5–7 обнаружен конкретный дефект текущей схемы: публичный API всегда формирует slug вида `build-<id>` и не устанавливает `smokeTest: true`, тогда как шаги установки в эмуляторе и проверки защищённой загрузки запускаются только для slug `smoke-*`; сервис подписи дополнительно требует `smokeTest: true` в записи задачи. Поэтому smoke-ветка существовала в workflow, но штатный пользовательский путь не мог создать подходящую задачу. Это объясняет, почему проверки очереди завершались без emulator/download steps.

В audit PR подготовлено исправление:

1. Добавлен отдельный `POST /api/internal/smoke-enqueue`, который требует GitHub OIDC из разрешённого workflow на `main`, создаёт только фиксированную тестовую HTML-страницу и не принимает пользовательский HTML.
2. Smoke-задача получает явный `smokeTest: true`, slug `smoke-*` и одноразовый тестовый download token; активные дубликаты блокируются.
3. Обычный claim пропускает smoke-задачи; тестовый запуск может забрать только конкретный request ID, возвращённый внутренним enqueue endpoint.
4. Добавлен ручной параметр workflow `smoke_test`, по умолчанию выключенный. При включении он запускает контролируемый цикл сборки, подписи, установки/запуска в Android Emulator и защищённой загрузки с проверкой SHA-256.
5. Добавлены тесты, подтверждающие, что внутренние enqueue/claim маршруты не работают без доверенного GitHub OIDC.
